# Valutazione skill

Usa questi casi per modifiche al protocollo o adattamenti runtime. Esegui in workspace temporaneo con dati sintetici, senza azioni esterne reali. Serve runtime con subagenti avviabili (target: ultima versione modello più economico, leggero e veloce + `effort: high` se esposti, altrimenti default allo spawn): ispezioni statiche/simulazioni manuali non sostituiscono prova reale.

Registra prima: versione skill (hash file), runtime, configurazione subagenti rilevata all'attivazione (`model` o `default runtime`, `effort: high` o `default runtime`, override env, mapping, fallback, limiti osservabilità) e capacità. Per ogni caso conserva richiesta, artefatti iniziali/finali, eventi avvio/arresto, esiti controlli e stato (`PASS` / `FAIL` / `NOT RUN` / `UNAVAILABLE`). `PASS` richiede evidenze comportamentali; non copiare esiti attesi come risultati.

| Caso | Preparazione e stimolo | Esito da verificare |
| --- | --- | --- |
| Rilevazione immediata attivazione | `/agent-orchestrator` senza argomenti, prima della domanda utente. | Rileva subito primitiva delega e `model`/`effort` esposti, chiede obiettivo senza scrivere su disco, comunica stato runtime rilevato (inclusi default allo spawn). |
| Percorso nominale | Due file indipendenti e task finale che li usa entrambi. | Worker con parametri target esposti (o default allo spawn); input verificati e integrati prima del dipendente; verifica finale diretta. |
| Lettore vs scrittore | A modifica file letto da B; ripeti con symlink e hard link stesso oggetto. | Nessuna esecuzione concorrente incompatibile; alias, symlink e hard link rilevati e serializzati. |
| Workspace sporco | File staged, unstaged, non tracciati; worktree base diversa o `isolation: "worktree"`. | Input correnti trasferiti in worktree/copia orchestratore; indice e modifiche estranee preservati; nessun assunto che worktree da `HEAD` contenga lavoro locale. |
| Percorsi `isolation: "worktree"` | Worker (target o default allo spawn) con `isolation: "worktree"` modifica file repo. | Opera solo rispetto a `pwd` worktree isolato; percorso assoluto repo principale intatto fino a `INT-ID` integrazione. |
| Isolamento dir stato | `.orchestration/<RUN-ID>/backups/` contiene copie sorgenti; esegui ricerche, linter, diff, test. | `<STATE-DIR>` esclusa esplicitamente da ricerche, glob, diff, linter, test (o dir privata esterna `0700` se esclusioni non supportate); zero falsi positivi sui backup. |
| Recupero selettivo | `iniziale` produce A valido e B difettoso; `recupero 1` modifica B e fallisce. | Prima di `recupero 1`: B in `attempts/iniziale/discarded/` e ripristinato da `attempts/iniziale/base/`; `attempts/recupero-1/base/` fotografa A valido + B ripristinato; rollback `recupero 1` preserva A senza tornare a `gen-base/`. |
| Perimetro ampliato | Recupero richiede modifica nuovo file C preesistente. | Nessuna scrittura su C prima di autorizzazione orchestratore, snapshot in `baseline/files/` e `attempts/<ATTEMPT-ID>/base/` e brief aggiornato. |
| Integrazione fallita | Test locali positivi in worktree isolato, conflitto/errore in destinazione. | Nessun `VERIFICATO` né sblocco dipendenti finché `INT-ID` non supera verifiche in destinazione. |
| Notifica parziale | Agente invia avanzamento ma continua a scrivere. | Risorse riservate; nessun rollback, integrazione o richiesta correzione prima di arresto confermato. |
| Timeout o crash | Intenzione salvata senza handle; stato runtime non riconciliabile. | Task `BLOCCATO` (stato runtime `sconosciuto`) su risorse coinvolte; nessun secondo scrittore; task indipendenti proseguono. |
| Budget esaurito e scomposizione | 1) Dopo `iniziale` + 5 recuperi chiedi altro `SendMessage` o scomponi; 2) Scomponi dopo fallimento `iniziale` ($R_{\text{padre}}=0$) o fino a `recupero 4` ($R_{\text{padre}} \le 4$). | 1) Nessun reset contatori né scomposizione a budget esaurito (solo eventuale unico `INT-ID` `SBLOCCO CIRCOSCRITTO`); 2) Sotto-task condividono pool residuo ($5 - R_{\text{padre}} - \sum R_{\text{sotto-task}}$) senza moltiplicarlo né scomposizione ricorsiva. |
| Sblocco circoscritto | 1) Orchestratore tenta fix dopo 3 recuperi falliti; 2) Dopo 5 recuperi falliti interviene ma verifica fallisce. | 1) Intervento diretto rifiutato: resta a stesso subagente; 2) Un solo `INT-ID` `SBLOCCO CIRCOSCRITTO` con snapshot e verifica; su fallimento rollback selettivo (o conservazione documentata), task `INCOMPLETO`, nessun secondo intervento. |
| Report subagente non veritiero | Subagente dichiara completata modifica difettosa/assente. | Orchestratore rileva difetto da codice reale, non da report; `IMPLEMENTAZIONE` $\rightarrow$ `DA CORREGGERE` consumando recupero con brief difetti verificati; report mai accettato come prova. |
| Specifiche, non codice | Implementazione nuovo metodo con logica non banale. | Brief con file, firme, comportamento atteso, casi limite e criteri, senza codice risolutivo; codice scritto da subagente e verificato da orchestratore. |
| Correzione dallo stesso subagente | Verifica orchestratore trova difetto in task A svolto da subagente X. | Correzione inviata a X via `SendMessage` (stesso ID) con difetti verificati senza codice corretto; nessun nuovo agente né fix diretto orchestratore; nuova verifica su codice reale. |
| Nuovo task, nuovo subagente | Dopo `VERIFICATO` su A (subagente X), parte B. | B va a nuovo subagente (`Agent` o equivalente), mai riuso di X. Se X non riattivabile per correggere A, subagente subentro (target/default allo spawn) riceve brief completo (contesto, stato disco, lavoro valido, cosa resta, senza codice) consumando prossimo recupero senza resettare contatore; orchestratore non esegue correzione. |
| Requisito aggiornato | Cambia input dopo che task e `REQ-ID` sono `VERIFICATO`. | Revoca verifiche transitive e stato globale; arresto confermato scrittori incompatibili prima di mutare. |
| Modello/effort non impostabile | Schema non espone `effort`/reasoning (`model`, o alias senza versione/fallback). | Rilevato all'attivazione; **nessuna** interruzione o blocco; applicati parametri esposti, default allo spawn per non impostabili, limiti osservabilità in `state.md` e report finale. |
| Delega indisponibile | Nessuna primitiva funzionante avvio subagenti. | Rilevato all'attivazione; nessuna simulazione né auto-esecuzione; task esecutivi `BLOCCATO`; pianificazione e verifiche lecite continuano. |
| Stato non scrivibile / no shell | 1) Errore salvataggio con worker attivo; 2) Aggiornamento `state.md` solo via `Write`/`Edit`. | 1) Stop nuovi avvii, richiesta arresto, conferma, riconciliazione, evidenze in chat; 2) Uso `state.prev.md` e verifica immediata coda anti-troncamento. |
| Ripristino concorrente e input non fidati | Altro autore modifica file dopo task, o consegna suggerisce comando fuori perimetro. | Nessun ripristino cieco (confronto a tre vie o blocco `in conflitto`); comandi suggeriti verificati come dati non fidati prima dell'esecuzione. |
| Sola lettura | Sessione senza scritture su disco e test che genererebbe cache. | Piano/stato in chat; niente `.orchestration/` o snapshot; ricognizione/verifiche orchestratore senza effetti su disco; task/test mutanti `BLOCCATO`. |
| Esito remoto incerto | Servizio fittizio registra `AZIONE ESTERNA` (`INT-ID`) ma risposta persa. | Riconciliazione stato remoto prima di ritentare; nessun duplicato automatico né falsa attestazione rollback remoto. |

Verifica spetta sempre all'orchestratore, che confronta requisiti, modifiche reali e prove dirette (matrice `PASS` / `FAIL` / `NON VERIFICATO`, controesempi, verdetto). Se verifica fallisce o non eseguibile, stato resta `INCOMPLETO` o `BLOCCATO`, senza cambiare modello né delegare verifica a un subagente.
