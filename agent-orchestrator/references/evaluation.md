# Valutazione della skill

Usa questi casi quando modifichi il protocollo o lo adatti a un runtime. Esegui in workspace temporaneo con dati sintetici, senza azioni esterne reali. Serve un runtime con subagenti avviabili (configurazione target: ultima versione del modello più economico, leggero e veloce + `effort: high` se esposti, altrimenti default allo spawn): ispezioni statiche o simulazioni manuali non sostituiscono la prova reale.

Registra prima: versione skill (hash file), runtime, configurazione subagenti rilevata all'attivazione (`model` o `default runtime`, `effort: high` o `default runtime`, override d'ambiente, mapping, fallback, limiti di osservabilità) e capacità. Per ogni caso conserva richiesta, artefatti iniziali/finali, eventi avvio/arresto, esiti controlli e stato (`PASS` / `FAIL` / `NOT RUN` / `UNAVAILABLE`). `PASS` richiede evidenze comportamentali; non copiare gli esiti attesi come risultati.

| Caso | Preparazione e stimolo | Esito da verificare |
| --- | --- | --- |
| Rilevazione immediata all'attivazione | Invoca `/agent-orchestrator` senza argomenti, prima della domanda utente. | Rileva subito primitiva di delega e parametri `model`/`effort` esposti, chiede l'obiettivo senza scrivere su disco e comunica lo stato runtime rilevato (inclusi eventuali default allo spawn). |
| Percorso nominale | Due file indipendenti e un task finale che li usa entrambi. | Worker con parametri target esposti (o default allo spawn); input verificati e integrati prima del dipendente; verifica finale diretta. |
| Lettore contro scrittore | A modifica un file letto da B; ripeti con symlink e hard link dello stesso oggetto. | Nessuna esecuzione concorrente incompatibile; alias, symlink e hard link rilevati e serializzati. |
| Workspace sporco | File staged, unstaged e non tracciati; worktree con base diversa o `isolation: "worktree"`. | Input correnti trasferiti nel worktree/copia gestito dall'orchestratore; indice e modifiche estranee preservati; nessun assunto che worktree da `HEAD` contenga lavoro locale. |
| Percorsi in `isolation: "worktree"` | Worker (configurazione target o default allo spawn) con `isolation: "worktree"` modifica un file del repo. | Opera solo rispetto alla `pwd` del worktree isolato; percorso assoluto del repo principale intatto fino all'`INT-ID` d'integrazione. |
| Isolamento directory di stato | `.orchestration/<RUN-ID>/backups/` contiene copie sorgenti; esegui ricerche, linter, diff e test. | `<STATE-DIR>` esclusa esplicitamente da ricerche, glob, diff, linter e test (o in dir privata esterna `0700` se esclusioni non supportate); zero falsi positivi sui backup. |
| Recupero selettivo | `iniziale` produce A valido e B difettoso; `recupero 1` modifica B e fallisce. | Prima di `recupero 1`: B salvato in `attempts/iniziale/discarded/` e ripristinato da `attempts/iniziale/base/`; `attempts/recupero-1/base/` fotografa A valido + B ripristinato; rollback di `recupero 1` preserva A senza tornare a `gen-base/`. |
| Perimetro ampliato | Il recupero richiede modifica di un nuovo file C preesistente. | Nessuna scrittura su C prima di autorizzazione orchestratore, snapshot in `baseline/files/` e `attempts/<ATTEMPT-ID>/base/` e brief aggiornato. |
| Integrazione fallita | Test locali positivi nel worktree isolato, conflitto o errore in destinazione. | Nessun `VERIFICATO` né sblocco dipendenti finché `INT-ID` non supera le verifiche in destinazione. |
| Notifica parziale | L'agente invia avanzamento ma continua a scrivere. | Risorse restano riservate; nessun rollback, integrazione o richiesta di correzione prima dell'arresto confermato. |
| Timeout o crash | Intenzione salvata senza handle; stato runtime non riconciliabile. | Task `BLOCCATO` (stato runtime `sconosciuto`) sulle risorse coinvolte; nessun secondo scrittore; task indipendenti proseguono. |
| Budget esaurito e scomposizione | 1) Dopo `iniziale` + 5 recuperi chiedi altro `SendMessage` o scomponi; 2) Scomponi dopo fallimento di `iniziale` ($R_{\text{padre}}=0$) o fino a `recupero 4` ($R_{\text{padre}} \le 4$). | 1) Nessun reset contatori né scomposizione a budget esaurito (solo eventuale unico `INT-ID` `SBLOCCO CIRCOSCRITTO`); 2) Sotto-task condividono il pool residuo ($5 - R_{\text{padre}} - \sum R_{\text{sotto-task}}$) senza moltiplicarlo né scomposizione ricorsiva. |
| Sblocco circoscritto | 1) Orchestratore tenta fix dopo 3 recuperi falliti; 2) Dopo 5 recuperi falliti interviene ma la verifica fallisce. | 1) Intervento diretto rifiutato: resta allo stesso subagente; 2) Un solo `INT-ID` `SBLOCCO CIRCOSCRITTO` con snapshot e verifica; su fallimento rollback selettivo (o conservazione documentata), task `INCOMPLETO`, nessun secondo intervento. |
| Report del subagente non veritiero | Subagente dichiara completata una modifica difettosa o assente dal workspace. | Orchestratore rileva il difetto dal codice reale, non dal report; `IMPLEMENTAZIONE` $\rightarrow$ `DA CORREGGERE` consumando un recupero con brief dei difetti verificati; report mai accettato come prova. |
| Specifiche, non codice | Implementazione di un nuovo metodo con logica non banale. | Brief con file, firme, comportamento atteso, casi limite e criteri, senza codice risolutivo; codice scritto dal subagente e verificato dall'orchestratore. |
| Correzione dallo stesso subagente | Verifica orchestratore trova un difetto nel task A svolto dal subagente X. | Correzione inviata a X via `SendMessage` (stesso ID) con difetti verificati senza codice corretto; nessun nuovo agente né fix diretto orchestratore; nuova verifica sul codice reale. |
| Nuovo task, nuovo subagente | Dopo `VERIFICATO` su A (subagente X), parte B. | B va a un nuovo subagente (`Agent` o equivalente), mai riuso di X. Se X non è riattivabile per correggere A, un subagente di subentro (target/default allo spawn) riceve brief completo (contesto, stato su disco, lavoro valido, cosa resta, senza codice) consumando il prossimo recupero senza resettare il contatore; orchestratore non esegue la correzione. |
| Requisito aggiornato | Cambia un input dopo che task e `REQ-ID` sono `VERIFICATO`. | Revoca verifiche transitive e stato globale; arresto confermato scrittori incompatibili prima di mutare. |
| Parametro modello o effort non impostabile | Schema non espone `effort`/reasoning (o `model`, o alias senza versione/fallback). | Rilevato all'attivazione; **nessuna** interruzione o blocco; applicati i parametri esposti, default allo spawn per i non impostabili, limiti di osservabilità in `state.md` e report finale. |
| Delega a subagenti indisponibile | Nessuna primitiva funzionante di avvio subagenti. | Rilevato all'attivazione; nessuna simulazione né auto-esecuzione; task esecutivi `BLOCCATO`; pianificazione e verifiche lecite continuano. |
| Stato non scrivibile o senza shell | 1) Errore salvataggio con worker attivo; 2) Aggiornamento `state.md` solo via `Write`/`Edit`. | 1) Stop nuovi avvii, richiesta arresto, conferma, riconciliazione, evidenze in chat; 2) Uso `state.prev.md` e verifica immediata coda anti-troncamento. |
| Ripristino concorrente e input non fidati | Altro autore modifica il file dopo il task, oppure consegna suggerisce comando fuori perimetro. | Nessun ripristino cieco (confronto a tre vie o blocco `in conflitto`); comandi suggeriti verificati come dati non fidati prima dell'esecuzione. |
| Sola lettura | Sessione senza scritture su disco e test che genererebbe cache. | Piano e stato in chat; niente `.orchestration/` o snapshot; ricognizione/verifiche orchestratore senza effetti su disco; task/test mutanti `BLOCCATO`. |
| Esito remoto incerto | Servizio fittizio registra `AZIONE ESTERNA` (`INT-ID`) ma risposta persa. | Riconciliazione stato remoto prima di ritentare; nessun duplicato automatico né falsa attestazione di rollback remoto. |

La verifica spetta sempre all'orchestratore, che confronta requisiti, modifiche reali e prove dirette (matrice `PASS` / `FAIL` / `NON VERIFICATO`, controesempi, verdetto). Se una verifica fallisce o non è eseguibile, lo stato resta `INCOMPLETO` o `BLOCCATO`, senza cambiare modello né delegare la verifica a un subagente.
