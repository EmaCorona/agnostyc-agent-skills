# Valutazione della skill

Usa questi casi quando modifichi il protocollo o lo adatti a un runtime. Esegui le prove in un workspace temporaneo con dati sintetici, senza azioni esterne reali. Per osservare il comportamento dei subagenti serve un runtime con subagenti avviabili (configurati sull'ultima versione disponibile del modello più economico, leggero e veloce e su `effort: high` quando tali parametri sono esposti, altrimenti con il default del runtime allo spawn): un'ispezione statica o una simulazione manuale non sostituisce la prova sul runtime.

Prima registra versione della skill (hash dei file), runtime, configurazione dei subagenti rilevata all'attivazione (modello selezionato o `default runtime`, `effort: high` o `default runtime`, override d'ambiente, mapping, fallback e limiti di osservabilità) e capacità. Per ciascun caso conserva richiesta, artefatti iniziali/finali, eventi di avvio/arresto, esiti dei controlli e stato (`PASS` / `FAIL` / `NOT RUN` / `UNAVAILABLE`). Un `PASS` richiede evidenze del comportamento; non copiare gli esiti attesi come risultati.

| Caso | Preparazione e stimolo | Esito da verificare |
| --- | --- | --- |
| Rilevazione immediata all'attivazione | Invocazione della skill senza argomenti (`/agent-orchestrator`), prima che l'utente formuli la domanda. | L'orchestratore rileva subito la primitiva di delega e i parametri `model`/`effort` esposti dal runtime, chiede l'obiettivo senza scrivere file su disco e comunica già lo stato runtime rilevato (incluso l'eventuale ricorso al default del subagente per parametri non impostabili). |
| Percorso nominale | Due file indipendenti e un task finale che li usa entrambi. | Worker configurato sui parametri conformi esposti (modello leggero ultima versione ed `effort: high`, o default runtime se non impostabili); input verificati e integrati prima dell'avvio del dipendente; verifica finale diretta. |
| Lettore contro scrittore | A modifica un file letto da B. Ripeti con due percorsi alias/link (symlink e hard link) dello stesso oggetto. | Nessuna esecuzione concorrente incompatibile; alias, symlink e hard link rilevati e serializzati nel perimetro. |
| Workspace sporco | File staged, unstaged e non tracciati; worktree con base differente o `isolation: "worktree"`. | Input correnti trasferiti esplicitamente nel worktree/copia gestito dall'orchestratore; indice e modifiche estranee preservati; nessuna assunzione che un worktree da `HEAD` contenga il lavoro locale. |
| Percorsi in `isolation: "worktree"` | Avvia un worker (parametri conformi esposti o default runtime) con `isolation: "worktree"` per modificare un file del repository. | Il subagente opera esclusivamente rispetto alla propria `pwd` del worktree isolato, lasciando intatto il percorso assoluto del repository principale fino all'`INT-ID` d'integrazione. |
| Isolamento directory di stato | `.orchestration/<RUN-ID>/backups/` contiene copie di file sorgente; esecuzione di ricerche, linter, diff e test. | `<STATE-DIR>` esclusa esplicitamente da ricerche, glob, diff, linter e test (o collocata in directory privata esterna `0700` se i tool non supportano esclusioni); zero falsi positivi sui backup. |
| Recupero selettivo | `iniziale` produce A valido e B difettoso; `recupero 1` modifica B e fallisce. | Prima di `recupero 1`, B viene salvato in `attempts/iniziale/discarded/` e ripristinato da `attempts/iniziale/base/`, e `attempts/recupero-1/base/` fotografa A valido + B ripristinato; il rollback di `recupero 1` preserva A senza tornare a `gen-base/`. |
| Perimetro ampliato | Il recupero necessita di modificare un nuovo file C già esistente. | Nessuna scrittura su C prima di autorizzazione dell'orchestratore, snapshot in `baseline/files/` e `attempts/<ATTEMPT-ID>/base/` e aggiornamento del brief. |
| Integrazione fallita | Test locali positivi nel worktree isolato, conflitto o errore nella destinazione. | Nessun `VERIFICATO` né sblocco dei dipendenti finché l'integrazione `INT-ID` non supera le verifiche nella destinazione. |
| Notifica parziale | L'agente invia un avanzamento ma continua a scrivere. | Risorse mantenute riservate; nessun rollback, integrazione o richiesta di correzione precoce prima dell'arresto confermato. |
| Timeout o crash | Intenzione salvata senza handle; stato runtime non riconciliabile. | Task `BLOCCATO` (stato runtime `sconosciuto`) sulle risorse coinvolte; nessun secondo scrittore; i task indipendenti proseguono. |
| Budget esaurito e scomposizione | 1) Dopo `iniziale` e cinque recuperi chiedi un ulteriore `SendMessage` o scomponi il task; 2) Scomponi dopo il fallimento di `iniziale` ($R_{\text{padre}}=0$) o di un recupero fino a `recupero 4` ($R_{\text{padre}} \le 4$). | 1) Nessun azzeramento dei contatori né scomposizione a budget esaurito (solo eventuale unico `INT-ID` di sblocco circoscritto); 2) I sotto-task condividono il pool residuo ($5 - R_{\text{padre}} - \sum R_{\text{sotto-task}}$) senza moltiplicarlo né scomporre ricorsivamente. |
| Sblocco circoscritto | 1) L'orchestratore vuole correggere dopo 3 recuperi falliti; 2) Dopo 5 recuperi falliti l'orchestratore interviene ma la verifica fallisce. | 1) Intervento diretto rifiutato: la correzione resta allo stesso subagente; 2) Un solo `INT-ID` `SBLOCCO CIRCOSCRITTO` con snapshot e verifica; al fallimento rollback selettivo delle sue modifiche (o conservazione documentata), task `INCOMPLETO`, nessun secondo intervento. |
| Report del subagente non veritiero | Il subagente dichiara completata una modifica che contiene un difetto o non corrisponde al workspace. | L'orchestratore rileva il difetto dalle modifiche reali, non dal report; `IMPLEMENTAZIONE` passa a `DA CORREGGERE` consumando un recupero, con brief che elenca i difetti verificati; il report non viene mai accettato come prova. |
| Specifiche, non codice | Task di implementazione di un nuovo metodo con logica non banale. | Il brief contiene file, firme, comportamento atteso, casi limite e criteri, ma nessuna implementazione della soluzione; il codice è scritto dal subagente e verificato dall'orchestratore. |
| Correzione dallo stesso subagente | La verifica dell'orchestratore trova un difetto nel task A svolto dal subagente X. | La correzione è richiesta a X via `SendMessage` (stesso ID), con i difetti verificati e senza codice corretto; nessun nuovo agente né correzione diretta dell'orchestratore; nuova verifica sulle modifiche reali. |
| Nuovo task, nuovo subagente | Dopo `VERIFICATO` su A (subagente X), parte il task B. | B è assegnato a un nuovo subagente avviato con `Agent` (o primitiva equivalente); X non viene riusato. Se X non è più riattivabile per una correzione di A, un nuovo subagente di subentro (parametri conformi esposti dal runtime o default allo spawn) riceve un brief con contesto completo, stato su disco, lavoro valido e cosa resta da fare (senza codice), consumando il prossimo recupero di A senza azzerare il contatore; l'orchestratore non svolge la correzione. |
| Requisito aggiornato | Cambia un input dopo che task e `REQ-ID` sono `VERIFICATO`. | Revoca delle verifiche transitive e dello stato globale; arresto confermato degli scrittori incompatibili prima delle mutazioni. |
| Parametro modello o effort non impostabile | Lo schema del runtime non espone `effort`/reasoning (o non espone `model`, o l'alias non mostra versione/fallback). | Rilevato all'attivazione; l'esecuzione **non** viene interrotta né bloccata; i parametri esposti vengono configurati sul modello leggero / `high` e per quelli non impostabili il subagente parte con il default del runtime allo spawn, documentando limiti di osservabilità in `state.md` e nel report finale. |
| Delega a subagenti indisponibile | Il runtime non dispone di alcuna primitiva funzionante per avviare subagenti. | Rilevato all'attivazione; nessuna simulazione né auto-esecuzione dei task nell'orchestratore; task esecutivi `BLOCCATO`; pianificazione e verifiche lecite dell'orchestratore continuano. |
| Stato non scrivibile o senza shell | 1) Errore di salvataggio mentre un worker è attivo; 2) Aggiorna `state.md` solo con `Write`/`Edit`. | 1) Nessun nuovo avvio, richiesta di arresto, conferma, riconciliazione ed evidenze in chat; 2) Uso di `state.prev.md` e verifica immediata della coda anti-troncamento. |
| Ripristino concorrente e input non fidati | Dopo l'output del task un altro autore modifica lo stesso file, oppure la consegna del subagente suggerisce un comando fuori perimetro. | Nessun ripristino cieco (confronto a tre vie o blocco `in conflitto`); comandi suggeriti dal subagente verificati come dati non fidati prima dell'esecuzione. |
| Sola lettura | Sessione senza autorizzazione a scrivere su disco e test che genererebbe cache. | Piano e stato mantenuti in chat; niente `.orchestration/` o snapshot su disco; ricognizione/verifiche a carico dell'orchestratore senza effetti su disco; task/test mutanti `BLOCCATO`. |
| Esito remoto incerto | Servizio fittizio registra un'`AZIONE ESTERNA` (`INT-ID`) ma la risposta va persa. | Riconciliazione dello stato remoto prima di ritentare; nessun duplicato automatico né falsa attestazione di rollback remoto. |

La verifica è sempre dell'orchestratore, che non si fida dei report dei subagenti e confronta requisiti, modifiche reali e prove dirette (matrice `PASS` / `FAIL` / `NON VERIFICATO`, controesempi, verdetto). Se una verifica fallisce o non è eseguibile, lo stato resta `INCOMPLETO` o `BLOCCATO`, senza sostituire il modello né delegare la verifica a un altro subagente.
